# ElRobot phone teleop: handoff (2026-10-17)

Read this first in a new session. It says where the project stands, what was decided and
measured, and what is left before the arm can be teleoperated with the iPhone.

## 1. The goal and the three layers

iPhone teleop of our ElRobot arm (7-DoF arm + gripper, 8 Feetech ST3215 servos on one serial
bus, Waveshare adapter at 1 Mbps, controlled from this Mac). Three layers:

| layer | what it does | status |
|---|---|---|
| **phone -> target** | iPhone ARKit pose + buttons over UDP; a "phone source" process turns it into TCP targets with deadlines (clutch, anchoring, gripper, guards) | **designed, not built** (prototype app streams packet v1; receiver only echoes) |
| **IK** | TCP pose -> 7 joint angles, per tick | **built and tested**, not wired into the pipeline |
| **executor** | target ring -> 250 Hz goal positions on the bus | **built, running on the real arm**; per-joint tuning in progress |

## 3. Decisions already made (do not re-litigate)

- **Calibration**: URDF zero kept; servo offsets centre each joint's range on 2048 (no 4095->0
  crossing in travel); signs 1-7 = +1, gripper = -1; gripper safe range 3.0..139.8 deg (hand
  sweep, not upstream's 126.2); joint 4 zero re-swept to 2012. Rest pose: shoulder -90, elbow 0,
  wrist pitch +90, rest 0, gripper open.
- **Teleop spec**: everything at **60 Hz** (ARKit rate); deadlines = phone capture time mapped to
  the Mac clock + **40 ms lead**, re-pinned at every clutch press (intervention counter bump);
  **15 Hz** critically damped filter with look-ahead; executor writes at **250 Hz**.
- **Teleop mode** = g1d's intervention path with **no policy** (`--teleop`): released clutch ->
  arm holds the last commanded pose.
- **Mapping**: phone pose drives the virtual **TCP** (tool-frame, relative to the clutch anchor).
  Phone grip: upright, screen facing LEFT (forward = ARKit -Y, left = +Z, up = -X; verify with a
  bench tool before moving anything). Tool- vs room-frame: still open.
- **Gripper**: hold-to-close; target width closes/opens at a fixed rate on device time; holds
  while the clutch is released; **squeeze bound** (command may lead the measured jaw toward closed
  by at most `squeeze_margin`, enforced in the bus process every tick; implemented in BusServo,
  default 5 deg, uncalibrated); anti-windup; hardware TORQUE_LIMIT on servo 8.
- Control box: this Mac. Camera exposure: "sticky". Cameras/recording/dashboard come after teleop.

## 4. The executor: what was measured on the arm (joint 6, +-5 deg sine at 0.25 Hz)

Loop: 4.00 ms period (p99 4.02), bus busy 44 %, command follows the 60 Hz target line exactly.
The executor itself is correct; what remains is how the servos follow.

| setting (joint 6) | amp | delay | reversal dead zone | hold err | err rms | mid-travel jolt |
|---|---|---|---|---|---|---|
| P32 (factory) | 97.5 % | 82 ms | 0.97 deg | -0.09 | 0.53 deg | 440 deg/s^2 |
| P48 | 98.9 % | 65 ms | 0.67 deg | -0.09 | 0.40 deg | 440 |
| P16 (LeRobot's) | 93 % | 132 ms | 1.65 deg | -0.09 | 0.92 deg | **220** |
| **P16 + friction 1.0** | **100.3 %** | **-18 ms** | **0.09 deg** | **-0.09** | **0.51 deg** | 440* |
| P16 + friction 1.5 | 103 % | -92 ms | 0.01 | +0.62 (overcompensated) | 0.72 | 220* |
| P48 + friction 0.5 | 100.2 % | -14 ms | 0.12 | +0.09 | 0.16 | 440 |

(*jolt is quantised: encoder 0.088 deg -> 220 deg/s^2 steps over 20 ms windows; treat as coarse.)

Findings:
- **Shaking happens only in motion.** Holding (no traffic, streaming every tick, or goals only on
  change) is calm. Cause: stick-slip of the moving joint (P-only servo vs static friction) and gear
  backlash knocking when the load changes sign at a reversal, shaking the printed arm; the other
  joints move inside their backlash, below one encoder step.
- **Lower P = smoother travel** (with D fixed, damping relative to stiffness rises): P16 felt
  clearly less shaky. Cost: lag, dead zone, sag.
- **Friction compensation** (`BusServo.friction`, goal leads the line by `f*tanh(v/2deg/s)`) fixes
  timing at the turns (P16: turn lag 520 -> 144 ms) but **not the turn-around jolt** (user feels no
  difference at reversals). 1.0 deg is right for P16; 1.5 overcompensates.
- **No effect / worse**: GOAL_SPEED cap near commanded speed (no change); D48 (much worse: 300 ms
  delay). Acceleration 0 works (no servo ramp).
- **Gravity sag**: joint 4 holds 1.8 deg low at P32 (17 % load). P16 would roughly double it.
- **"Sluggish servo" state**: once, after a mixed session, joint 6 tracked with 5x the lag at the
  same load though all registers were normal; **a 12 V power-cycle cleared it**. If a run shows
  amp < ~95 % or delay > ~100 ms unexpectedly, power-cycle before concluding anything.
- LeRobot (SO-101) writes P16 I0 D32 to STS3215s; lerobot issues #1333, #930 report similar
  jitter; no definitive fix exists online.

## 5. Next steps, in order

### A. Finish the executor tuning (current work)
1. **Per-joint gains and friction in the executor** (agreed): make `p_coef`, `d_coef` (keep 32),
   `friction` per joint in `ExecutorSettings`/driver config instead of test flags; write P at
   connect, restore at release. Start: light joints (5 forearm roll, 6 wrist bend, 7 wrist roll,
   8 gripper) **P16 + friction 1.0 deg** (gripper: no friction; squeeze bound owns it).
2. **Gravity-loaded joints (2 shoulder, 3 elbow, 4 wrist pitch, also 1 base)**: run the sine
   test per joint at P16 / P32 (`--joints 4`, etc.); joint 2 rests on its stop at rest, so test it
   in another pose. Expect gravity to preload the gears (less knock at turns) but more sag.
3. **Gravity compensation** (agreed): sag ~= gravity torque / servo stiffness. Plan: identify
   each joint's compliance (deg of hold error per unit gravity torque) from holds in a few poses
   (measured hold error vs URDF gravity torque from `elrobot_model.py`/MuJoCo), then command
   `q_goal = q_line + C * tau_g(q_line)`. Keep MuJoCo out of the 250 Hz loop (P7 rule): compute the
   offset in the target writer (P6/IK side, 60 Hz) or a light analytic model, and pass it in the
   target row or a side ring. Design not decided.
4. Optional: measure the felt vibration with the iPhone accelerometer (phyphox) taped to the
   gripper; the encoders cannot see it.

## 7. How to run things (from `ElRobotRepo/`)

```bash
cd elrobot_deploy && uv sync --extra runtime          # deploy env (includes ../elrobot)
uv run pytest -q tests/test_bus_executor.py           # executor tests (no hardware)
uv run python -m elrobot_deploy.cli.executor_test --sim --joints 6 --yes      # simulated
uv run python -m elrobot_deploy.cli.executor_test --joints 6 --p-coef 16 --friction-deg 1.0
#   other flags: --hold SECONDS, --d-coef, --goal-speed, --rewrite-every N, --amp-deg, --freq,
#   --dry-run. The summary prints amp/delay/dead zone/hold err/error/smoothness.
cd .. && uv run python -m elrobot.calibration --show  # live joint angles (read-only)
uv run python -m elrobot.relax                        # torque off everywhere
uv run pytest -q                                      # root repo tests (62)
```

## 8. Gotchas

- **ST3215 multi-turn offset trap**: never write an offset with torque on; power-cycle after
  writing offsets; no joint may cross 4095->0 while powered (the centring offsets prevent it).
- Torque left on by a crashed/old run: the executor refuses to start ("torque is already on");
  run `elrobot.relax` (support the arm first). The executor never turns off torque it didn't
  turn on.
- The `VIRTUAL_ENV ... will be ignored` warning from uv is harmless.
- In a worktree session, git commands may not touch the main checkout; the user merges with
  `git merge --ff-only <branch>` from `ElRobotRepo/`.
- Don't run `ruff --fix` over the whole package: it rewrites ~80 inherited g1d files.
- User preferences: explain before acting on hardware; never command motion without the user's go.
